18. **App-level plugins are subgraphs (not separate runtimes); per-plugin DID + UCAN; layered consent.** Ben's framing (2026-05-10 conversation, post-Phase-3-close pre-v1 cleanup window). Plugins are **shareable subgraphs** of the engine's own operation primitives — handlers, materializers, SANDBOX nodes, READ/WRITE/etc. — content-addressed, importable / replicatable / editable across Atriums. There is no separate plugin runtime: the engine evaluator walks plugin subgraphs the same way it walks any handler, with the active principal switched to the plugin's identity for the walk's duration.

    **Trust model = three layers:**
    - **(a) User-as-root.** Every capability chain traces back to a user-issued root grant. No plugin gets capability without user consent at *some* point in the chain. This anchors trust end-to-end and survives Phase 8 decentralized plugin discovery — when registries are P2P, the user-mint root is still the trust anchor.
    - **(b) Install-time manifest.** Each plugin ships a manifest with two halves: `requires` (caps the plugin needs to function) and `shares` (policy for what other plugins are allowed to receive from this one). The user reviews the manifest at install and consents to the *envelope*, not to each runtime access. Both halves are signed by the plugin author so they can't drift post-install.
    - **(c) Runtime delegation within manifest envelope.** Plugins delegate UCANs to each other freely *if and only if* the request fits the source plugin's manifest `shares` policy. The CapabilityPolicy backend validates the chain at access-time: chain traces to user-root + each delegation step fits source plugin's policy + requested cap is within attenuation envelope.

    **Engine-side surface (Class B β SHIPPED at PR #184 in pre-v1 cleanup window):** the evaluator's read pathway threads the active principal via `Engine::read_node_as(principal, cid)` — the public surface for any read attributed to a non-trusted principal. Engine internals (IVM, sync, view materialization, audit) call `Engine::get_node(cid)` — the engine-internal un-attributed read pathway, no permission check, no overhead on hot paths. **v1-assessment-window question (per `docs/future/phase-4-backlog.md §4.43`):** `Engine::get_node` is currently `pub` (originally intended `pub(crate)` per the initial bake-in framing), which exposes the un-attributed read at the napi binding layer. Plugin authors **never call either function** — they author graph nodes; the evaluator is the only caller of `_as`. The 4 `todo!()` stubs at `crates/benten-engine/src/engine_wait.rs:1011-1026` that were β-shaped and were the migration target are CLOSED at HEAD — those line numbers now host the real `get_node_label_only` / `put_node` / `read_node_as` / `resolve_subgraph_cid_for_test` implementations from PR #184.     **Implementation refinements ratified 2026-05-11 conversation (Phase-4-Foundation pre-R1 triage):**

    - **Plugin identity = four distinct concepts, not conflated.** Earlier framing collapsed these into a single "plugin DID" with attestation chain back to user-DID; that imported the device-DID-attestation pattern unnecessarily and conflated provenance with runtime-authority. The proper separation:
        1. **Content-CID** — what the plugin IS (canonical bytes of its subgraph + manifest)
        2. **Peer-DID signature on original content** — provenance (who originally authored + shared it; verifiable via signatures; RotationLog handles revocation)
        3. **Plugin-DID minted at install** — a UCAN audience handle (NOT an attested sub-identity); just an identifier so the user can issue UCAN caps with `audience=plugin-DID`
        4. **User-DID** — trust anchor + signs install records (consent + local commitment) + issues UCAN caps with audience=plugin-DID
    - **No device-DID-attestation chain for plugins.** Devices ARE attested sub-identities because they represent physical hardware the user owns; plugins are code running inside the user's engine and don't need that chain. Plugin-DID is purely a UCAN audience handle.
    - **Cross-plugin/schema references use content-CID, not author-DID.** Plugin Y declares `accepts_content: [hash1, hash2, ...]` rather than `accepts_author: [alice_did, ...]`. Each version increments the CID. No stable author-DID needed for the system to work.
    - **User-as-source signing model.** When a user installs a plugin (including admin UI v0), user-DID signs the install record in the user's graph. The plugin's original content carries peer-DID signatures from whoever shared/authored it; the install record is a local-anchor signed by the user. No Benten-project-key needed.
    - **Workflow ↔ plugin unification.** A workflow IS a plugin IS a subgraph. Single shape, distinguished by **scale + sharing intent** (manifest presence). Promoting a workflow to a plugin = adding a manifest; no fundamental shape change. Composition: meta-plugins reference sub-plugins (recursive). Composition-cycle detection at install time builds a structural `Subgraph` representation of the composition graph (one `PrimitiveKind::Read` Node per visited manifest CID + `COMPOSES`-labelled edges per reference) + walks that subgraph via a DFS visited-on-stack tracker — no new `PrimitiveKind` variant minted (CLAUDE.md #1 12-primitive irreducibility preserved). The structural walker is internal to `benten_platform_foundation::plugin_manifest::detect_composition_cycle`; the future migration to the full engine evaluator (which would require library-as-active-subgraph + evaluator handoff) is named for Phase-4-Meta.
    - **Plugin library subgraph + active references.** User's full plugin set lives as a real `benten_core::Subgraph` (handler_id = `"plugin-library"`) containing all installed versions + forks: one `library_root` Read Node + one `anchor::<plugin_name>` Read Node per distinct plugin-name (Phase-1 [`benten_core::version::Anchor`] companion) + one `version::<cid>` Read Node per installed CID. Edges: `library_root → anchor` (label `ITEM_TYPE`, from the schema-vocabulary container-of-element edge), `anchor → version` (label `VERSION_OF`), `anchor → active-version` (label `CURRENT`, per-device-local per ratification #2). Active graph holds references to specific plugin-versions currently in use. Switching active version = updating the `CURRENT` edge. Keeps old/unused versions in the library (cheap, content-addressed) without polluting the active graph. No new `PrimitiveKind` variant minted.
    - **Versioning via existing Phase-1 anchor + Version Node pattern, extended to DAG-shape.** Linear version-chain extended to support branches (forks). Anchor → v1 → {v2-mainline, v1.5-fork}; CURRENT can point at any branch tip. Each installed CID lands as a `version::<cid>` Read Node in the plugin-library subgraph + (where the install extends the mainline tip) is appended to the per-name `benten_core::version::Anchor` chain via `benten_core::version::append_version`. Fork installs (append against a non-tip prior head) surface `VersionError::Branched` at the Anchor surface; the library treats this as a legitimate DAG-shape fork (the Version Node still lands in the subgraph for retention; the linear-chain just doesn't extend past the fork point). Per-user-local version history; updates are PULL-not-PUSH (no manifest schema versioning needed — CID covers shape).
    - **Revocation reuses Phase-3 infrastructure.** Cap revocation via UCAN per-grant (already shipped; G16-B-F per-row recheck). Provenance rotation via `benten-id` RotationLog (already shipped). Plugin-install path consults both; no net-new revocation tooling needed in Phase 4-Foundation.

    **Private namespaces** (plugins saving their own private data): plugin's writes go to a DID-scoped namespace; namespace cap is held by plugin's DID; manifest `shares=none` for that namespace blocks delegation. Engine refuses to issue cross-plugin caps for private namespaces. Gives plugins a sovereign space (AI agents' working memory, intermediate state, journals) without breaking cross-plugin sharing semantics.

    **Principal primitive — authority half vs confidentiality half (framing ratified 2026-05-18; coupling clarification, not a re-debate).** "User" and "plugin" are the SAME primitive — a `Principal` (`system:Principal` Node / per-DID identity) with a content-addressed subgraph the evaluator walks "as" that principal (`read_node_as`), scoped by `private:<did>:*` capability scopes. That primitive has TWO isolation halves: **(1) Authority isolation — "who is *allowed* to see/act"** = capability-gated (UCAN/`CapabilityPolicy` + private-namespace delegation-refusal). This is SHIPPED and real, and is sufficient on a single *cooperating/trusted* engine. **(2) Confidentiality isolation — "who *can read the bytes*"** = per-principal encryption of the storage partition. This is NOT built (redb is plaintext; only transport + signing crypto exist) and is UNSCHEDULED. Capabilities only bind a cooperating engine: the moment a principal's subgraph rests on hardware another principal controls (peers-hold-ciphertext / E2EE subgraphs / Phase-7 Garden-Grove untrusted-host / Phase-8 decentralized plugin hosting / Kith selective-disclosure), capabilities give ZERO protection — encryption is the load-bearing substrate there. Therefore "**multi-tenancy = capability scopes**" (as stated unconditionally in `docs/ENGINE-SPEC.md:312` and the v1-spec archive) is **true only on a trusted engine and misleading for every untrusted-host phase** — that doc line needs a trusted-engine qualifier (tracked in issue #1301). The confidentiality half = the codepoint-dispatched encryption envelope from the #5 crypto-agility refinement, sealing a per-DID storage partition. The two coupled, currently-un-scheduled pieces: **#989** (structural storage-partition seam: `WriteContext::namespace_did` + per-DID backend view — the hook encryption plugs into; a Ben-decision Phase-4-Meta v1-API fork) and **#1301** (the encryption-as-confidentiality + multi-tenant-substrate initiative — roadmap placement is a Ben decision; technical shape settled by the crypto-agility contract). Future agent proposals that treat capability-gating as delivering confidentiality/multi-tenant isolation on an untrusted host, or that scope encryption without PQ-hybrid-from-its-first-format-version, must be rejected with reference to this framing + the #5 refinement.

    **Trajectory alignment:** v1 (Phase 4 — Foundation ships manifest schema + admin UI v0 + install-time consent; Meta layers self-composing admin on top) — small N, user reviews each manifest, simple. Phase 6 (AI agents) — manifest declares "I integrate with calendar / notes / email"; user consents at install; agent runs autonomously without per-action prompts.     **What this rules out:** pure user-as-root with per-action prompts (fails Phase 6 AI-agent ergonomics); pure UCAN-native peer delegation without manifest envelope (fails user-sovereign framing — "I installed A, didn't agree to A handing my data to B"). 2. **When triage says "fix now" — write the actual code.** Don't say "noted for implementation."
3. **Stay in the current phase.** Flag scope detours explicitly; let Ben decide.
4. **Mini-review after EVERY implementation group.** One correctness agent, properly briefed.
5. **No deprecated aliases or backward-compat shims.** Fresh project. Delete, don't comment.
6. **Doc updates in the LAST implementation group,** not afterthought.
7. **Explain in plain English first,** technical details second.
8. **Don't combine agents.** Each gets its own prompt.
9. **Full quality council for feature phases.** Only pure correctness work gets a reduced council.
   - **Iterate-to-convergence generalized (Ben-ratified 2026-05-19).** The iterate-until-convergence discipline is NOT R6-only. Every ADDL review tier that **(a) gates an artifact, (b) whose triage mutates that artifact, and (c) is not re-reviewed by a downstream converging tier** iterates: full council → triage → re-review the EDITED artifact → repeat until a full round returns 0 substantive (BLOCKER/MAJOR) findings, then advance. Scope = **R1 + R4 + R4b + R6**. **Pre-work critics + per-group R5 mini-reviews stay single-pass** (feeders re-caught by a downstream converging tier; iterating them is redundant/cost-explosive). Termination = the strict Q5 rule reused verbatim (full council every round; only BLOCKER/MAJOR block; pattern-induction additive). Rationale: triage at R1/R4/R4b mutates the artifact and a single pass never re-reviews the post-fix state (the gap Q5 closes at R6, one tier up); front-loaded convergence *shortens* the R6 cycle. Full record + inclusion test + proof-cases: memory `feedback_iterate_critical_reviews_to_convergence` + `docs/DEVELOPMENT-METHODOLOGY.md`.
10. **Ben is a co-architect.** Present options, not just results. His questions reshape the plan.
11. **Run the full test suite after every commit.** Not just the packages you changed.
12. **HARD RULE — there is no "later". No time threshold. No importance distinction. Default disposition for any finding is FIX-NOW.** ONLY THREE legitimate non-fix-now dispositions (Ben's framing 2026-04-27): **(a) OUT OF SCOPE** with explicit reason; **(b) BELONGS-ELSEWHERE-SPECIFICALLY** — the work genuinely belongs in another NAMED doc/repo + the destination receives the entry NOW (not "I'll add it later"; "carry to next brief" is NOT a named destination); **(c) DISAGREE-WITH-EXPLANATION** — articulate why the recommendation isn't correct (cite conflicts/alternatives). Anything else (`carry to brief X` / `Phase-2c follow-up` / `defer-with-doc` without specific destination / `would be nice to have` / `note for next wave` / `<N min is too much to fix inline` / `minor enough to defer`) is NEVER valid. The rule has NO time qualifier and NO importance qualifier. If you find yourself typing those non-valid phrases — STOP. If something was skipped, RELAUNCH (a fresh agent dispatch is the right cost to pay). Ben has had to remind me THREE+ TIMES — this is the project's most repeatedly-violated principle. See memory `feedback_no_defer_HARD_RULE` (loud-CAPS title, intentional) for the full disposition flowchart + 2-softer-exception examples + failed-instance log.
13. **Parallelism cap — MAX 7 concurrent in-flight IMPLEMENTER agents + LIGHTWEIGHT scoped pre-flight + sccache + cargo-clean-idle.** Empirically verified across two 2026-04-27 OOM crashes (first with 7+1 agents in flight; second with 3 agents but disk at 96% used) initially set the cap at 3. Raised to 4-5 on 2026-04-29 by Ben after wave-8 close demonstrated the scoped-pre-flight + sccache + cargo-clean-idle disciplines hold capacity at 4 implementer worktrees + 1 read-only audit without OOM. **Raised to 7 on 2026-05-07 by Ben after wave-7/wave-7b ran cleanly at 4 + extended observation (several days, no crashes, plenty of storage headroom).** Ben is willing to test the higher cap on parallelizable work; the 3 disciplines (scoped pre-flight + sccache + cargo-clean-idle) make the higher cap safe. **Read-only review/audit agents (R1, R2, R4b, R6 lenses, deep-investigation lenses, scoping plans) are cap-EXEMPT** — they don't compile or run cargo, so they don't contribute to RAM/disk pressure. The 7 cap applies to IMPLEMENTER agents only. Apply the cap PRE-DISPATCH at every wave boundary. Use rolling dispatch (kick off next as a slot frees) within a wave; full pause at wave boundaries. **Three coupled disciplines (ratified Tier 2 2026-04-27):**
    - **Scoped pre-flight only.** Agents NEVER run workspace cargo (`cargo check --workspace`, `clippy --workspace`, `nextest run --workspace`, `doc --workspace`). Run scoped per-package check + single-package clippy + fmt; CI is the authoritative full-workspace verifier. If a dispatch brief asks for workspace cargo, agent DECLINES + surfaces the over-prescription. Per-agent RAM peak drops from 2-4 GB to ~500 MB. See `dispatch-conventions.md` §3.
    - **sccache** (`brew install sccache` + `~/.cargo/config.toml` rustc-wrapper). 20 GB shared compile cache at `~/Library/Caches/Mozilla.sccache`. wasmtime + napi-rs + heavy transitive deps compile ONCE across all worktrees. `sccache --show-stats` to monitor hit rate. See `dispatch-conventions.md` §3.1.
    - **Cargo-clean-idle.** When a worktree is between fix-pass cycles (mini-review in flight, idle >30 min), `cargo clean` to free target/ disk. Rebuild via sccache is fast (~2-3 min). NOT applied to worktrees with uncommitted in-progress work. Per-wave-boundary audit: `df -h /Users` >90% used → pre-emptively cargo-clean idle worktrees (the graduated valve for the 90-97% band). See `dispatch-conventions.md` §3.2.

    Pair with worktree-disk-hygiene rule (drop worktree+local-branch immediately on PR merge; audit `du -sh ../benten-wt-*` at every wave boundary; delete stale backup directories outside the project). Cap value `7` is laptop-specific (raised from `3` → `4-5` → `7` across 2026-04-29 + 2026-05-07; each step validated by extended observation under the disciplines). **HARD-ABORT threshold for new dispatch = disk >97% used** (raised from ~92% by Ben 2026-06-02; the 90-97% band is managed by cargo-clean-idle as the graduated valve, NOT by halting — we have sccache + scoped-pre-flight + worktree-drop-on-merge holding steady-state, and most current work is light-compile red-phase test stubs). When OOM still happens despite the cap, check `df -h` first — disk pressure >90% can cause cascading RAM exhaustion via macOS file cache eviction (manage it by cleaning idle worktrees, not by stopping below 97%). See memory `feedback_worktree_disk_hygiene` for full principle + recovery pattern when agents are killed mid-flight (worktrees often retain uncommitted work — re-dispatch fresh agent INTO the same worktree with brief "resume from current state" rather than restart-fresh + per pim-19 §3.11 checkpoint-pre-flight-discipline).

14. **HARD RULE 12 extends to the STANDING LEDGERS, not just to fresh findings** (Ben 2026-07-27, restated verbatim: *"our principle is to do everything now that we don't either disagree with for a specific reason or doesn't make more sense somewhere specific later in our plan"*). A named Compromise in `docs/SECURITY-POSTURE.md` or a D-row in `docs/V1-FROZEN-INTERFACE-DEFERRED.md` **satisfies the letter of clause (b) while potentially laundering a deferral that has no real justification.** The ledger records a decision; it does not justify it. Re-audit the whole ledger before any phase-close tag, sorting into three buckets — **LEAVE** (depends on un-landed work / gated on an external event / a deliberate accepted risk we'd choose again) · **DO-NOW** (honestly stated but the reason doesn't hold up — cost, size, effort, risk-aversion, "matches existing pattern", "for now X is fine" all land here) · **FALSE-RECORD** (the entry asserts a closure/mechanism/mitigation that does not exist in the code — *not a deferral at all*, but an inaccurate permanent record, and the worst defect available on a freeze because it makes the signed document overstate what the binary enforces). For every "closed by X / mitigated by X / enforced by X / covered by X", go find X; if it exists, ask whether deleting it would fail anything. See memory `feedback_compromise_ledger_not_exempt_from_hard_rule`.

15. **When a doc and the code disagree, the default is to change the CODE** (Ben 2026-07-27, GAP-5). Retense the doc **only** when we have actually decided we don't want the property it describes — never merely because the code is harder to change. Retensing prose is always the cheapest way to turn a red finding green, it is invisible afterwards (the artifact ends up self-consistent), and on a freeze it silently ratifies the weaker behaviour forever. The deciding question is not "which is cheaper" but *"if we were writing this from scratch today, which one would we write?"* **Price the code-side fix before concluding the doc-side one is pragmatic** — GAP-5 looked like "build a vault" and was actually "wire the already-frozen, already-byte-pinned vault primitive to a file path." The usual correct answer is a split: code→doc for the *behaviour* (a fallback that cannot deliver its guarantee must fail closed with a typed error, never silently fake success), doc→code for the *disclosure* (a false claim comes out immediately regardless), and any genuinely-deferred remainder reaches a destination row that receives the entry in the same commit. A review finding that says only "doc and code disagree" has done half the job — require it to say **which one is wrong and why**, or the fixer will pick whichever is cheaper. See memory `feedback_doc_code_mismatch_fix_the_code`.
