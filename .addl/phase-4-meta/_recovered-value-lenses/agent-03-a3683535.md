# `Value::Decimal` — option space, ranked

## Conclusion first

**Do not add `Value::Decimal`. Do not add a tag-based extension seam — it is not available at any price.** But the requester is *right about a real defect*, and it is not the one they named: **the expression evaluator silently converts integers to floats on division** (`crates/benten-eval/src/expr/eval.rs:551-555`). Integer minor units — the standard mitigation, and the thing Option A depends on — **do not survive the engine's own TRANSFORM evaluator.** That is a live, silent, money-relevant bug that exists whether or not `Decimal` is ever added.

Ranked: **A′ (do nothing on `Value`, fix the evaluator + close two record gaps) ≫ D ≫ C ≫ B.**

**The reframe that motivated this pass is false.** Major type 6 is not unclaimed — it is claimed by the DAG-CBOR spec, closed, and its one permitted value is already taken by CIDs. I'll show that first because it removes B and C from contention on structural grounds, not preference.

---

## 1. The reframe collapses — verified three ways

**Spec.** The IPLD DAG-CBOR spec is normative and explicit: *"Use no tags other than the CID tag (42). A valid DAG-CBOR encoder must not encode using any additional tags and a valid DAG-CBOR decoder must reject objects containing additional tags as invalid."* It names **bignums and bigfloats** among the forbidden — i.e. tags 4 and 5, precisely what the reframe proposed. (Confidence: high — direct spec text.)

**Codec.** `serde_ipld_dagcbor-0.6.4/src/de.rs:308,324` routes `major::TAG => de.deserialize_cid(visitor)`; `de.rs:213-219` matches the tag number and returns `DecodeError::TypeMismatch` for anything that isn't `CBOR_TAGS_CID`, which is `42` (`lib.rs:148`). The serializer has no general tag-emission path — only CID tag 42 (`ser.rs:613`).

**Correction to the briefing's premise.** "Deserialize is hand-written, so decode behaviour on an unrecognised shape is OURS to define" is **true only for shapes the codec forwards, and false for tags.** The codec rejects the tag *before* dispatching to our visitor. Our visitor (`value.rs:185-292`) has no `visit_newtype_struct` at all — even tag 42 would fail if it ever reached us. We have no say here.

**The deeper problem, which would survive even a codec fork.** Benten's CID prefix *asserts* `0x71` = dag-cbor (`crates/benten-core/src/lib.rs:151`, `:459`, `:493`; enforced at `:493`). Emitting a non-42 tag produces bytes that are not DAG-CBOR while the content identifier claims they are. That is a self-inconsistent content address — strictly worse than the float bug, because it breaks the *identity* layer rather than an arithmetic layer.

> **`Value` is not the frozen type that is missing an agility seam. It is a type whose underlying space is already closed by someone else.** That distinction is the load-bearing insight of this pass, and §5 turns it into the missing record.

---

## 2. Two more structural blockers on Option B

**No discriminated space exists.** The encoding is `#[serde(untagged)]` (`value.rs:79`) and keyed on CBOR major type. With tags forbidden, any new variant must **reuse** a major type already claimed:
- Decimal-as-2-element-array is byte-identical to `Value::List([Int, Int])`, and `visit_seq` unconditionally returns `Value::List` (`value.rs:255-273`).
- Decimal-as-map is byte-identical to `Value::Map`, and `visit_map` unconditionally returns `Value::Map` (`value.rs:279-291`).

There is no bit anywhere to tell them apart. Escaping this means abandoning `untagged`, which rewrites every Node's canonical bytes and changes the sentinel CID `bafyr4if…mwduda` pinned at `docs/V1-WIRE-FORMAT-INVENTORY.md:23`. That is not a variant addition; it is a new wire format.

**`i128` is not encodable.** `ser.rs:286-295` rejects any `i128` outside `[-u64::MAX-1, u64::MAX]`. The requester's literal ask — `unscaled: i128` — yields a value **constructible in Rust that fails at encode time**: a new partial function of exactly the `Float(NaN)` shape the module docs (`value.rs:8-17`) exist to apologise for. Adding a second instance of the project's most-documented wart, days before freezing it, is a poor trade. (Confidence: high.)

**The scale-normalisation tension the brief flagged as the most interesting question — resolved, and it dissolves.** `1.500` vs `1.5` as distinct encodings is *directly incompatible* with canonical-bytes determinism: two values that compare equal must hash equal, or `PartialEq` (derived, `value.rs:78`) desynchronises from CID equality and Inv-style content addressing breaks. You would have to choose scale-significance (breaks determinism) or normalisation (reintroduces the requester's bug at the wire layer). **There is no third option inside a content-addressed store.** The resolution is that scale is *presentation/schema metadata, not value identity* — which is exactly what §4 recommends, and is how the project already handles this class of problem.

## 3. The finding the requester should have led with

`crates/benten-eval/src/expr/eval.rs:544-562`:

```rust
(Value::Int(a), Value::Int(b)) => {
    if *b == 0 { return Err(EvalError::new("division by zero")); }
    // Integer division if evenly divisible; else promote to float.
    if a % b == 0 { Ok(Value::Int(a / b)) }
    else { Ok(Value::Float((*a as f64) / (*b as f64))) }
}
```

**A `TRANSFORM` node computing `total_cents / 3` returns a `Float`.** The value's *type* changes based on its *data*. This is silent, data-dependent, and lands squarely on the split-tender / proportional-tax-allocation / discount-proration operations a revenue system performs constantly.

This matters far beyond the museum case: it means **"model money as integer minor units" — the project's own correct default and the entire foundation of Option A — is not actually safe inside Benten today.** The requester argued the engine lacks a decimal type. The sharper claim available to them was that the engine *manufactures floats from integers*, which is worse, because it defeats the workaround they were told to use.

Related, lower severity: `add` uses `wrapping_add` (`eval.rs:520`) — silent wrap rather than a typed error. And `values_equal` (`:596-601`) makes `Int(1) == Float(1.0)` true while the derived `PartialEq` on `Value` (`value.rs:78`) says false — two equality notions in one system.

**The numeric tower is also entirely undocumented.** No arithmetic semantics in `docs/DSL-SPECIFICATION.md`; `docs/ENGINE-SPEC.md` — cited in CLAUDE.md's reading list as item 5 — **does not exist in `docs/`**. So this behaviour is about to be frozen with no written contract at all. (Confidence: high for the code; the missing-file observation is a side finding worth its own row.)

## 4. The options, argued at strength

### A′ — Do nothing to `Value`; fix the evaluator; close the record gaps ★ RECOMMENDED

**Strongest form:** the standing bias (`feedback_engine_primitives_vs_application_layer`) says compose at the application layer first. An application models a decimal as `Map{unscaled: Int, scale: Int}` — which is *precisely* what a `Decimal` variant would encode to anyway, since tags are forbidden. **The wire bytes are identical either way.** The only difference is whether the engine knows the semantics. So the honest question is not "can applications do this" but "what would the engine *do* with the knowledge" — and the answer is: nothing it does today, because it has no decimal arithmetic, no decimal ordering, and no decimal rendering to offer.

**Freeze-coupling:** zero for the `Map` recipe. The evaluator fix is *behaviourally* freeze-coupled (changing it post-tag is a behaviour break, though not a wire break) — so it is genuinely now-or-soon.

**What is honestly lost** (specific, per the brief's request):
| Facility | Sees an app-layer decimal? |
|---|---|
| Canonical bytes / CID | ✅ Yes — `Map` hashes deterministically, `to_canonical` recurses (`value.rs:400-406`) |
| DAG-CBOR round-trip | ✅ Yes |
| IVM views / indexes | ⚠️ Structurally yes, semantically no — `crates/benten-graph/src/indexes.rs` keys on bit-exact encoded equality (`:20-21`); two equal decimals at different scales index as distinct keys |
| Expression evaluator | ❌ No — `add`/`compare`/`divide` reject `Map` operands (`eval.rs:525,540,560,592`); ordering and arithmetic are unavailable |
| DSL literals | ❌ No literal syntax; an object literal |
| TS type mapping | ➖ **Neutral — and this is the surprise.** `packages/engine/src/types.ts:33-40` maps `Value` to JS `number` (an IEEE-754 double), and napi routes through `serde_json::Value::Number` (`bindings/napi/src/node.rs:136-161,323-325`). **A `Decimal` variant would have no faithful JS-primitive representation either** — TS would need an object or string, i.e. the `Map` shape again. The requester's "invisible to other consumers" argument is *weakest exactly at the boundary their web application would use.* |

So the real loss is **ordering and arithmetic in the evaluator**, not encoding or cross-language visibility. That is a genuine loss and I do not want to minimise it — but note it is the *same* facility that Option B would also have to build from scratch, and that §3 shows is currently broken even for `Int`.

### D — Scale as schema metadata ★ SECOND, and the project already does this

`crates/benten-platform-foundation/src/schema_compiler/vocab.rs:163-182` defines `Scalar` with:
- `BytesCid` — *"Maps to `Value::Bytes` with a documented CID interpretation"* (`:174-176`)
- `TimestampHlc` — *"int carries the HLC ticks. Maps to `Value::Int` with HLC interpretation"* (`:177-179`)

**This directly answers the brief's "what other variants would we regret not having?" question — and the answer is decisive.** Timestamps and CIDs are two of the three obvious candidates, they are *far* more central to Benten than decimals are, and **the project already decided not to give either one a `Value` variant.** It layered interpretation in the schema vocabulary instead, and the mechanism has held. A `Scalar::Decimal { scale }` mapping to `Value::Int` (unscaled minor units, scale in the schema) is a *post-freeze-additive* extension of an existing, proven pattern — `Scalar` lives in `benten-platform-foundation`, not in the frozen wire core.

Because that answer is "no, and we have precedent" rather than "yes, several," **the brief's own test resolves against a seam (C) and toward B being unnecessary.**

### C — A general extension seam ✗ REJECT, but here is its honest strongest form

The tag-based version is **structurally impossible** (§1). The steelman is a *data-model* seam: reserve a sentinel map key (e.g. leading `"/"`, mirroring DAG-JSON's own CID convention) so the hand-written visitor could promote `{"/dec": [...]}` to a typed variant, with a typed-reject arm for unknown extension names. That **is** technically available, needs no codec change, changes no existing bytes, and is genuinely now-or-never (post-tag it would break anyone already using that key).

**Why reject it anyway:**
1. It injects a *new decode-ambiguity class* into `Value::deserialize` — the leaf of every DAG-CBOR decode path in the workspace (node bodies, subgraph payloads, sync frames, UCAN bytes at the napi boundary, per `value.rs:106-113`). That is the single hottest and most security-sensitive decode surface, hardened only recently for DoS (`MAX_VALUE_DECODE_DEPTH`, `value.rs:139`).
2. Doing that days before a freeze, immediately after a falsification sweep found **17 of 36 enforcement claims unenforced**, with no committed adopter, is the wrong risk trade at the wrong moment.
3. It buys nothing Option D doesn't already buy without touching frozen bytes.

**The anomaly it appeals to has a good answer.** Baked-in #5 demands agility because *cryptographic algorithms get broken by cryptanalysis* — the space moves. `Value`'s variant set is pinned to the **CBOR major-type set**, an IANA-governed space that is closed, stable, and older than the project. `Value` does not need an agility seam because **its underlying space does not move.** That is the principled reason there is no seam — and §5 shows nobody has ever written it down.

### B — `Value::Decimal { unscaled, scale }` ✗ REJECT

Blocked by three independent structural facts: no discriminated encoding space (§2), `i128` unencodable (§2), and scale-significance irreconcilable with canonical bytes (§2). Its motivating benefit — first-classness — is largely unrealisable at the TS boundary anyway (§4/A′). Its strongest residual argument is the Rust-API one in §5, which is better served by a documented carve-out than by a variant.

## 5. A record gap found on the way — independent of the decimal decision

**`benten_core::Value` carries no `#[non_exhaustive]`** (`value.rs:78-80`; confirmed machine-visibly at `docs/public-api/benten-core.txt:720` — `pub enum benten_core::value::Value` with no attribute, contrasted with `:219 #[non_exhaustive] pub enum benten_core::subgraph::PrimitiveKind`).

`docs/V1-FROZEN-INTERFACE.md:1249-1330` (item 11) declares **"MAXIMALIST application… APPLY `#[non_exhaustive]` UNIVERSALLY unless a D8-carve-out has a documented structural reason,"** and enumerates its carve-outs: `benten-caps::Scope`, `PrimitiveKind`, `GraphError::TxAborted`, `GrantRejection`, `BindingContext`. **`Value` appears in neither the must-apply table nor the carve-out set.** It is simply absent — despite being the property type on every Node and Edge.

**My read is that a carve-out is substantively correct and only the rationale is missing** — `Value` is a frozen-cardinality wire-keying enum in exactly the sense item 11 already recognises (one variant per CBOR major type; the set is closed by the spec, not by us). So this is a **gap in the record, not a defect in the code** — but it is the shape CLAUDE.md rule 14 names as *the worst defect available on a freeze*: a signed document asserting coverage it does not have. Worth closing in one paragraph before the tag.

Relatedly: **no test anywhere pins tag-rejection.** `grep` across `crates/benten-core/tests/` finds no `0xd8` byte-level assertion. "DAG-CBOR forbids all tags but 42" is a load-bearing decode guarantee with zero enforcement — textbook falsification-sweep shape, and cheap to close.
