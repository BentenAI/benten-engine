# Bounded resources as single-owner admission — completing §3.4

**Status: R0-INPUT.** This is a design record, not a plan. Per the ADDL observance rule the build gets its own R0→R1 pipeline when scheduled; this document is that pipeline's input, the way `binding-grammar.md` fed §3.1 and `ivm-aggregation.md` fed §3.3. Written 2026-08-10 out of the engine-fit-and-gaps investigation (`docs/future/engine-fit-and-gaps.md` §3.4), synthesized from 4 adversarially-verified lenses; conflicts resolved with the verification evidence at worktree `07b882a4`.

---

## 1. The answer in a paragraph

Benten expresses "at most N" as **single-owner admission**: a bound is declared as data (a content-addressed `bound:decl` node binding an admission label to a capacity, edited only under its own capability scope, with the version chain as its free audit trail per baked-in #8); exactly one engine — the declared `UptimePolicy::AlwaysOn` peer (baked-in #17, `crates/benten-id/src/device_attestation.rs:71-77`) — holds the admit grant and is the only place admissions commit; and the admission check runs **inside the commit's own serialization domain** — an in-transaction count against committed state plus the batch's own writes, at the graph-layer commit boundary, below every write-entry family. A non-owner cannot mint an admission (no grant, refused locally by a cooperating engine; killed at every honest peer's per-row merge recheck otherwise), so all admissions serialize at one engine and the owner's local state *is* the truth — which is exactly why the museum's 204,371-booking replay measured single-owner at **91.6% local at any replica count** while escrow fell from 58.9% to 30.5%. The invariant enforced is the honest one the museum's own production revealed: **never exceed silently**. Refusal is a typed domain outcome carrying `{available, bound, owner_did}` (the F# `Error 10` contract); override is a first-class attributed write through the same guard under a distinct scope, visible in the reporting views ("13 sold / 12 cap, 1 override"); waitlist is pure application graph. Nothing here is a 13th primitive — `executionPolicy` stays a dispatch policy on handlers (baked-in #1), gaining an `owner` value that routes admission calls to the bound's owner. State the theorem once and stop re-deriving it: **this invariant class is not coordination-free (Bailis et al., PVLDB 8(3), 2014); escrow relocates coordination, nothing removes it; single-owner concentrates all of it at the one peer the replay measured as cheapest.**

## 2. The serial point

**Where admission is made sound, in one sentence: the redb write transaction is the serial point, and the check must live inside it — in the graph layer, below every entry.**

The machinery, first-hand-verified:

- **The serial point exists.** redb 4.1.0's `begin_write` is a true blocking single-writer lock (vendored `redb-4.1.0/src/db.rs:1031-1036`), and a write transaction's reads see committed state plus its own pending writes (write-through contract at `crates/benten-graph/src/transaction.rs:8-11`; the Inv-13 existence probe reads `NODES_TABLE` inside the open write txn at `:409-412`). The codebase already states this soundness argument about itself at `redb_backend.rs:1463-1476` — the bounded-resource check is the same shape with `count < C` in place of `absent`.
- **Nothing can currently read inside it.** `benten_graph::Transaction` exposes puts and deletes only (`transaction.rs:346-705`); `EngineTransaction` likewise (`engine_transaction.rs:95-166`). Every existing count opens its own separate read txn (`engine_diagnostics.rs:134-136` → `redb_backend.rs:1309-1313`) — TOCTOU-broken as an admission read by construction. The build's one structural addition: **an additive in-tx count method** (e.g. `Transaction::count_by_property(label, prop, value)`), whose machinery is adjacent (`PROP_INDEX_TABLE` opened in-txn at `transaction.rs:440`; write-through at `:429-448`; in-tx removal on delete at `:591-599`). Cost: an O(k) index read, k ≤ C+oversell ≈ ≤~400, tens of microseconds inside a 1-10ms commit cycle (`crates/benten-graph/benches/concurrent_writers.rs:1-30` §14.6). No counter-cache node at v1 — it fights content-addressing; named revisit-iff k ≫ 10³.
- **The check sits in the graph layer because "the single commit boundary" is actually three families** (the decisive verification finding): (i) the `Engine::transaction` wrapper — where the capability gate already runs post-writes/pre-commit inside the closure (`engine_diagnostics.rs:44-110`, deny at `:84-90`), covering dispatch replay (`engine.rs:4198-4231`); (ii) **direct `backend.transaction` callers** — `Engine::create_node` (`engine_crud.rs:78`) and `Engine::append_version` (`engine_diagnostics.rs:572-575`), the latter being **the sync-merge terminal write** (`engine.rs:1782`), i.e. the exact two-tills ingress; (iii) the privileged `put_node_with_context` family (`redb_backend.rs:854-862, 1505`), which takes redb's lock directly and never touches the `TxGuard`. A check homed only in family (i) ships the oversell as a design. The correctness contract, stated as the invariant the falsification sweep will test: **admission state is read inside the serialization domain of the commit that writes it, and the check sits below all three entry families.** In-repo precedent for both the pattern and the placement exists — the Mutex-serialized check-and-record critical section at `crates/benten-engine/src/install_record_replay.rs:1-60` and the pre-write admission-reject seam at `write_boundary_chain_validator.rs:1-40`; this is not greenfield concurrency design.
- **The refusal is a domain outcome, not an infra error.** Precedent is exact: `cap_error_to_outcome` and `system_zone_to_outcome` at `engine.rs:4241-4244`; `BoundExceeded { limit, current, available }` is the third arm of that match, with `available` clamped at 0 (post-override occupancy can exceed C; the raw signed figure is reporting data, not refusal payload). The deny-at-commit test shape already exists at `redb_backend.rs:2215-2262` (`transaction_with_deny_on_commit`).
- **Why the walk can never enforce (and why the fold can never be the enforcement read).** The walk is two-phase: reads hit live committed state per-call, writes buffer and replay later in one tx (`primitive_host.rs:8-35, 250-303`; `engine.rs:4198-4231`) — a BRANCH-gated admission decides in a different transaction than the write it gates, and WAIT can stretch the gap arbitrarily (`engine_wait.rs`). The IVM view is disqualified separately and permanently: the tx guard is deliberately released **before** subscriber fan-out (#645, `redb_backend.rs:2181-2200`), so transaction N+1 can be admitted before N's events reach any view. Re-inverting #645 was considered and declined — slow subscribers back inside the write lock, for nothing the O(k) scan doesn't already give.
- **The honest wrinkle, worse than one lens claimed: the `TxGuard` is fail-fast and the collision is shipped today.** A concurrent `.transaction()` gets `NestedTransactionNotSupported` immediately (`transaction.rs:230-244`; `redb_backend.rs:2097-2137`) — it errors, it does not queue. Verification established this is reachable at HEAD: `apply_atrium_merge` is async on the engine's own tokio runtime (`engine.rs:1215`), pushes no active-call frame, and takes the `TxGuard` via `append_version`, concurrently with any napi-driven replay. Two consequences for the record: **v1 admissions run single-flight through the owner's admission service** (a liveness *and* correctness obligation, application-owned at v1), and a **thread-keyed blocking guard** (same-thread → nested error, cross-thread → queue on redb's already-blocking lock) is named near-mandatory hardening, not contingent hardening. The adjacent pre-existing defect must be named, not papered over: truly concurrent walks cross-contaminate the shared active-call frame stack (`engine.rs:873, 3887-3936`; `primitive_host.rs:370-384`) under napi's documented thread-safety contract — an interlock the admission work inherits, tracked in the receiving row.

**The enforcement-vs-reporting split, stated once for §3.3 and §3.4 together:** the *enforcement* read is the owner's in-transaction index count — committed state plus own batch, inside the serial point, never the view. The *reporting* read is the D-106 fold — per-engine, any staleness, anywhere. Multi-peer balance remains a reporting concern (`ivm-aggregation.md` §9.1); enforcement never needs it. A handler-side BRANCH pre-check reading the fold is legitimate **UX** ("check twice, enforce once") with a monotone-safety property — under exclusivity, staleness can only overcount, refusing too eagerly and never overselling — whose premises are explicit: the admission seam holds exclusivity over *all* writes on the label (edits emit `Created`, `ivm-aggregation.md:23`), and a grant-backed policy is installed (on the default `NoAuthBackend`, the capability-topology half is void; the in-tx commit guard still binds locally regardless — it is policy-independent).

**Falsification arms** (the tests that fail if the serial point is removed): (1) N threads × M admissions against C, retry-on-fail-fast; final ≤ C, admitted+refused = N·M, every refusal's `available` consistent with a serializable history — mutations that must flip it RED: move the count to a pre-tx read, **or route the write via `create_node`/`append_version` around the check**; (2) walk-TOCTOU negative control via the `test_pre_dispatch_gate` barrier (`engine.rs:3911-3921`) — oversell *must* occur handler-side, documenting the unsoundness; (3) view-lag pin — admission-by-fold-read over-admits (the #645 window is structural); (4) own-writes arm — one tx admitting 2 with C−1 sold refuses the second *within the batch*; (5) override arm — a privileged over-bound write still lands counted and attributed (never-exceed-*silently*); mutation: route the override around the tx → RED.

## 3. Ownership and routing

**Ownership is an exclusive write-capability, not a new mechanism.** "Peer P owns bound B" = only P's principal holds the label-derived admit scope (scope-from-label derivation is the shipped Phase-1 contract, `crates/benten-caps/src/grant_backed.rs:9, 283-286`). The **record is discovery and audit; the grant is law** — a peer believing a stale record still cannot mint admissions.

- **The record:** two ordinary-label, content-addressed node kinds — `bound:decl { bound_id, capacity, unit, admission_label, hlc }` and `bound:ownership { bound_cid, owner_principal, epoch, predecessor, reach?, hlc }` — append-only, epoch-chained, reduced deterministically by (epoch, HLC, CID) using the LWW rule the CRDT layer already pins (`crates/benten-sync/src/crdt.rs:828-882`). Add-wins keeps conflicting transfers *visible by construction* (two records, same predecessor — an auditable fork, never a silent resolution). Declined homes, on first-hand evidence: a `system:`-zone record (sync ingest rejects system-zone mutations, `engine.rs:1319-1336`, `crdt.rs:50-63` row-4b — it would silently not propagate) and a CURRENT-pointer (moves in memory with no event, `engine_diagnostics.rs:592`).
- **REQUIREMENT (from adversarial verification, load-bearing): each bound's admission label and override label map to a dedicated sync zone.** The per-row merge recheck that gives ownership its cross-peer teeth (`SyncRevokedDuringSession`, `engine.rs:1390-1418`; `docs/SECURITY-POSTURE.md:1952`, PR #161) is **zone-granular** — it evaluates `"{zone}:write"` (`engine.rs:1371, 1402-1408`), never `store:admission:<bound>:write`, and the explicit-scope override in `derive_write_scope_from_ctx` (`grant_backed.rs:297-301`) means a non-cooperating till holding *any* zone-write authority would pass the recheck for forged admission rows. Bound-per-zone placement (feasible — `apply_atrium_merge` takes `zone: &str` per call) makes the zone check label-equivalent with zero protocol change. Without this coupling the enforcement story has a hole exactly oversell-shaped.
- **Routing at v1 is application-layer thin-client, and the gap is precisely enumerable.** Shipped: `Engine::call_as` (`engine.rs:3634-3644`), the IPC method allowlist with `engine.call_as` cap-bound (`crates/benten-renderer-tauri/src/lib.rs:127-161`), authenticated session→principal with no client-asserted principal (`thin_client_bridge.rs:19-29`), the three-rung gate (`lib.rs:497-560`). Missing: the `Transport::Http` wire framing (declared-unbuilt, `thin_client.rs:607-615`; no HTTP server dep anywhere in the workspace) and the owner-side admission command handler (`dispatch_ipc` gates only; "the method-specific handler lives in the integrator binary"). Both are glue on shipped seams, no freeze contact. A till reads the (synced) ownership record locally and calls the owner.
- **v1 ships static, capability-held ownership; leader election is declined.** `PLATFORM-DESIGN.md:383` concedes election is unspecified; with one always-on box and a manager holding the transfer scope, there is nothing for a quorum to decide. `executionPolicy` gains an **`owner`** value — dispatch reads the bound's ownership record — which mostly *dissolves* the `:383` open question rather than answering it. Transfer = one attributed transaction: new `bound:ownership{epoch+1}` + revoke old admit grant (revocation is an insert, `engine_caps.rs:200-220`) + issue new — riding the shipped revocation-MUST-win machinery (HLC-monotonic rejection + durable ordering + per-row recheck, `SECURITY-POSTURE.md:1949-1963`); we mint no "ownership-MUST-win" policy.
- **Degradation:** the non-owner's local write path is refused **by construction** (no grant) — fail-closed is structural, there is no "fall back to local" to forbid. Owner-unreachable surfaces a typed refusal at the till with **`available` absent — never a stale number presented as live** (`E_BOUND_OWNER_UNREACHABLE`-class mint). For the museum's LAN, the partition that severs till→server-closet usually took the switch down — recorded as the accepted failure mode, with their caveat carried verbatim: till↔till partition frequency is UNMEASURED. Honestly: the ~8.4% of sessions needing owner coordination become remote calls, and **refusals under partition** — a named degradation with the peer→owner forward envelope as the named additive path, not a non-gap.
- **Reclaim:** committed rows are durable and sync out on the owner's return; uncommitted walks are visible refusals. The stale-owner window (old owner commits post-revocation while partitioned) resolves at merge: those rows **void visibly at reconciliation** via the per-row recheck — refused, never silent. Operational rule, not protocol: transfer only when the old owner is confirmed down.
- **The override, stated positively:** exceeding the bound is a *designed, first-class write* — distinct label (`admission-override:<bound>`), distinct scope granted to manager principals, routed **through the same commit guard** so it is counted and carries the attribution triple (`store.rs:484-525`) plus `{reason, over_cap, qty}` forever. Occupancy = Count(admission) + Count(override), two D-106 label views summed at the read site — and the commit-time count covers **both** labels, so an override landing mid-flight cannot corrupt an admission's arithmetic. The display reads "13 sold / 12 cap (1 override: T. Ortiz)" — the museum's 12-seat-camp-shows-13 reality made legible. Silence is structurally impossible: every over-bound entry either refused typed or carries an attributed override marker.

## 6. Considered and declined

- **Escrow / reservation-lease / bounded-counter CRDTs** — declined on measurement, not taste: 91.6% local at any replica count vs 58.9%→30.5%, tying or losing in every capacity band at n=8; the crossover is `C` vs `n·q_p99`, and a 12-seat camp at n=3 with p99 party 9 has *nothing to lease* (100% of sessions degenerate). Theorem: not coordination-free (Bailis et al., PVLDB 8(3), 2014) — escrow relocates coordination, nothing removes it. **Revisit iff `C > 3·n·q_p99` AND demand genuinely multi-homed — both, measured** (recorded in the §4.172 row so it is findable when field data arrives).
- **Enforcement in `CapabilityPolicy` via a properties field** — the lean context is a recorded layering decision, not an accident (`policy.rs:86-89`: richer shapes "would require `benten-caps` to take a direct dep on `benten-graph` (a layering break)"); D-102 confirmed from both sides. The sealed trait is untouched; the bound check is engine/graph-internal.
- **Enforcement in BRANCH** — structurally advisory forever (two-phase walk, §2); it is the UX check, never the guard.
- **The fold view as the enforcement read** — guard drops before fan-out (#645); re-inverting it was moved-for-cause. Permanent split: index-in-tx enforces, fold reports.
- **A per-bound engine mutex outside the tx / lock-around admission section** — a second serialization domain that must be proven consistent with the redb one; the in-tx read makes it unnecessary. (Resolves the composition lens's lock-around proposal against the atomicity lens's rejection — the additive read method wins.)
- **A 13th "ADMIT" primitive** — admission is READ+BRANCH+WRITE+RESPOND over a commit-boundary guard; the guard is dispatch/commit machinery, exactly what `executionPolicy` was already specified as.
- **SANDBOX-side counting** — baked-in #16; a wasm counter is a parallel write path bypassing the guard.
- **`system:`-zone ownership record; CURRENT-pointer ownership** — don't sync / don't emit (§3, first-hand evidence).
- **Leader election at v1** — unspecified in its own source doc; static capability-held ownership is what the replay measured, and manual attributed transfer is the honest failover.
- **Counter-cache node** — fights content-addressing; the O(k) scan is self-healing ground truth; revisit-iff k ≫ 10³.
- **Refusal as engine error** — a policy refusal is data (routed edge + `available`); only transport failure is a typed error.

## 7. What we tell the museum

Declare each session's capacity as data; the box-office server (your always-on peer) owns admissions. Every sale commits there, checked inside the same transaction that writes it — two tills cannot each sell the last seat, whether concurrent or offline, because a till that can't reach the owner gets a **refusal that says what's left** (or "availability unknown — owner unreachable", never a stale number). Staff overselling is not fought, it's *modeled*: a manager's override goes through the same gate, is counted, attributed, and visible — "13 sold / 12 cap (1 override)" — your +186 anomaly becomes an audit trail instead of a mystery. Waitlists are ordinary app data. **What this design rests on from your §5.5 caveats:** (a) your till↔till partition frequency is UNMEASURED — we adopt your LAN assumption that a partition severing till→owner usually severs everything, and if field data shows till-up/owner-down is common, that triggers the recorded escrow re-test (`C > 3·n·q_p99` AND multi-homed demand), not an ad-hoc redesign; (b) your ~8.4% non-local sessions become remote calls to the owner, and refusals when partitioned — we state that as the trade the 91.6% number bought; (c) your deliberate-oversell practice is load-bearing for the design — "never exceed silently" is the invariant precisely because your production told us the hard bound was already fiction.

## 8. Open questions (genuinely undecidable from code)

1. **Merge-recheck authority binding in relay topologies** — the per-row recheck evaluates the *session peer's* authority, resolved once per merge (`engine.rs:1285`), not the row author's. For direct owner↔till sessions this is fine; for gossip/relay paths, whose authority *should* it evaluate, and does the owner's admit-grant chain reach every till (AuthorizationGrant distribution per RATIFIED-S&C §R3)? R1 verification item, question rewritten per verification C3.
2. **WAIT-suspension × buffered-ops interplay** — how pending ops survive suspend/resume envelopes was asserted, never traced; pins the width of the walk-TOCTOU window but changes no conclusion (the walk is advisory regardless).
3. **Quantity representation** — one-row-per-unit (default; keeps the check property-free and count = row count) vs a `qty` property (the graph-layer check *can* read node bodies, unlike the cap policy). R1 decides; falsification arm 4 covers both.
4. **Sync-ingress re-validation** — whether handler subgraphs arriving via Atrium re-run `validate_subgraph`; moot for the decided annotation home, load-bearing only if key-in-content is ever revisited. Flagged, unverified either way.
